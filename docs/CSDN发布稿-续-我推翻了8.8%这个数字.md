# 一次景点数据爬取复盘（续）：我把「8.8% 脏数据」这个数字彻底推翻了

> 续自上一篇《一次景点数据爬取复盘：从 499 条到 455 条，我剔掉的 8.8% 脏数据》。
> 上一篇写于项目早期 v1 阶段，那一版清洗只做了一半，结论也是错的。
> 这篇讲我后来发现了什么、以及为什么我要把自己的结论推翻。
> 完整代码：https://github.com/koilxz/city-attraction-analysis

## 先说结论

上一篇我说："499 条数据里有 44 条脏数据，污染率 8.8%，清洗后剩 455 条。"

**这个数字是错的。**

真实情况是：499 条里只有 **348 条**属于"我以为的那种脏数据"（跨城市重复抓取），而真正致命的问题——**景点根本不在这个城市**——我一条都没查出来。

最终清洗结果是 **151 条**，不是 455 条。污染率不是 8.8%，而是 **69.7%**（`clean.py` 日志原文：`合计剔除: 348 条剩余: 151 条` / `保留率: 30.3%`）。

| | 上一篇（v1） | 这一版（v3） |
|---|---|---|
| 识别出的问题 | 跨城市重复 | 重复 + **系统性城市误标** + 伪造字段 + 伪零分 |
| 清洗后剩余 | 455 条 | **151 条** |
| 声称污染率 | 8.8% | **69.7%** |
| 结论可信度 | ❌ 假干净 | ✅ 双向校验通过 |

一句话总结这个过程：**v1 的数据"看起来很干净"，不是因为它干净，而是因为我的检查规则太弱。**

## 一、被我放过的第一个信号：重复抓取

这部分上一篇写对了。旅游网站的列表页底部有「相关推荐 / 猜你喜欢」模块，我的爬虫把这些推荐位的内容也抓了下来。

同一个景点出现在多个城市的列表里：

- `sight_id` 完全重复的：**123 条**，涉及 **97 组**
- 按 `sight_id` 跨城市去重后：499 → 376 条

这一步我做对了，但也就停在这里了。

## 二、我漏掉的第二个信号：字段是假的

某天我突然想到一个问题：**我用来验证"这个景点属于哪个城市"的那个字段，是真的吗？**

我去翻自己的爬虫代码，找到了这段：

```python
# spider_real.py（v1 版本，节选）
def fake_coord(city):
    """按城市中心生成一个坐标"""
    centers = {"北京": (39.90, 116.40), "上海": (31.23, 121.47), ...}
    return centers[city]   # ← 同一个城市的所有景点，坐标完全一样
```

而 `distance`（距离市中心距离）字段：

```python
spot["distance"] = round(random.uniform(0.5, 30), 2)   # ← 随机数
```

也就是说，**`latitude` / `longitude` / `distance` 这三个字段全是假的**，是脚本编出来的。

我当时脑子里有一个很具体的计划：**用经纬度反查来校验景点归属**。

当我知道这件事的时候，那个计划直接作废了。

处理方式：三个字段全部从数据集中删除，README 里主动写明这个局限。

> 这一条是整个项目里最让我后怕的。如果我当初"用经纬度校验"并且跑通了，我会以为自己做了个很严谨的交叉验证——实际上我是在用一个自己造的假数据去验证真实数据。**错得越自信，越难发现。**

## 三、真正的问题：系统性城市误标

删掉假坐标之后，我失去了"自动校验归属"的能力。只能换一条路：**逐条人工核验**。

在开始之前，我先试着让规则去抓。写了三类规则：

1. **去重规则**：`sight_id` 出现在多个城市 → 误标
2. **地标规则**：名字里含其他城市名（如"杭州西湖"出现在上海） → 误标
3. **省市信号规则**：简介里提到的省市与标注城市不符 → 误标

跑完一看，残留的疑似记录只有十几条。我以为快收工了。

然后我去人工看。**第一页就发现了漏网的。**

青岛的列表里有：

- **蜈支洲岛**（海南三亚）
- **蓬莱阁**（山东烟台）
- **刘公岛**（山东威海）
- **孔庙**（山东济宁）

这四个地名，**没有一条能被上面三类规则抓到**：

| 规则 | 为什么失效 |
|---|---|
| 去重规则 | 它们在本市列表里只出现一次，不构成重复 |
| 地标规则 | "蜈支洲岛""蓬莱阁""刘公岛""孔庙"名字里**不含任何城市名** |
| 省市信号规则 | 蓬莱、刘公岛、孔庙**都在山东省内**，和标注城市"青岛"同省 ⇒ 信号"一致" |

**这就是"系统性"三个字的含义**：这不是零散的脏数据，是一整类我的规则设计根本没考虑过的情况——**景点在省内但不在本市**。

`clean.py` 的实际剔除日志（`src/clean.py` 运行输出）：

```
[步骤3] 跨城市去重（按 sight_id）
  剔除记录              : 167 条
[步骤4] 单条记录的定位冲突
  剔除记录: 181 条
    [重庆] 芙蓉镇          ← 地标归属冲突(湘西)
    [重庆] 凤凰古城         ← 地标归属冲突(湘西)
    [重庆] 沱江欣赏苗家吊脚楼   ← 核验表：实属湖南湘西州
    [重庆] 张家界国家森林公园   ← 地标归属冲突(张家界)
    [重庆] 黄龙洞景区        ← 核验表：实属湖南张家界
[步骤4b] 「真实归属核验表」覆盖校验
  核验表条目       : 128 条
  据此剔除记录     : 156 条
  合计剔除: 348 条   剩余: 151 条
```

注意 `[步骤4]` 里两种剔除理由的分工：**「地标归属冲突」是规则自动抓到的，「核验表」是我人工核验补上的**。后者占了 156 条 —— 如果没有那张人工表，这 156 条会全部漏掉，而且日志上看不出任何异常。

一旦找到第一个，剩下的就是顺着往下看。我把 279 个景点逐条过了一遍，产出一张**128 条**的「景点全名 → 真实归属」核验表。

`clean.py` 里这张表是这样参与清洗的：

```python
from foreign_map import FOREIGN_MAP   # 128 条人工核验表

# 精确匹配优先：表里有记录的，以表为准
key = f"{row['name']}"
if key in FOREIGN_MAP:
    row["city"] = FOREIGN_MAP[key]
```

关键在于用的是**精确匹配**而不是模糊匹配。因为我试过模糊匹配（比如"兵马俑"去匹配"兵马俑博物院"），结果把"西安城墙"误命中成"西安"——**规则越智能，错误越难查**。

## 四、清洗后我做了什么：9 项双向校验

数据删掉了 348 条，我必须证明**没有误杀**。所以写了这个脚本：

```python
# verify_clean.py（节选）
checks = [
    ("核验表外地景点残留", ...),      # ① 该删的删干净了吗
    ("跨城市重复 sight_id", ...),      # ② 重复清零了吗
    ("城市数", ...),                   # ③ 10 个城市还在吗
    ("每城景点数", ...),               # ④ 会不会有城市被删空了
    ("伪造字段残留", ...),             # ⑤ 假字段删干净了吗
    ("伪零分记录", ...),               # ⑥ 0 分处理了吗
    ("同城同名重复", ...),             # ⑦ 新的重复形态
    ("关键景点误杀", ...),             # ⑧ 双向校验：不该删的删了吗
    ("污染样本残留", ...),             # ⑨ 已知脏样本清零了吗
]
```

实跑结果：

```
  ✅ ① 核验表外地景点残留 = 0（应为 0）  []
  ✅ ② 跨城市重复 sight_id = 0 组（应为 0）
  ✅ ③ 城市数 = 10（应为 10）
  ✅ ④ 每城景点数 11~18（最少应 ≥8）
  ✅ ⑤ 伪造字段残留 = []（应为空）
  ✅ ⑥ 伪零分记录（评分=0 且评论=0）= 0
  ✅ ⑦ 同城同名重复 = 0
  ✅ ⑧ 关键景点误杀 = 0 []
  ✅ ⑨ 污染样本残留 = 0 []
======================================================================
结果：9 通过 / 0 失败
```

**注意 ④ 和 ⑧**：④ 检查"没有城市被删空"，⑧ 检查"关键景点没被误杀"。只做"该删的删了吗"是不够的——**清洗脚本最容易的失败方式就是删得太多而且自己不知道**。

## 五、还有个没注意到的坑：0 分不等于差评

清洗过程中我发现原始数据里有 13 条记录评分 = 0。查了才发现平台的编码逻辑：

```
rating = 0  且  comment_count = 0   →  实际是「从未有人评价过」
```

它不是"0 分差评"，是"**没有数据**"。这两件事混在一起，会把所有评分统计拉低。

处理：置为缺失值，按城市均值填补。这 13 条里有 **11 条**在去重后仍留在最终数据集里（另 2 条本来就属于被剔除的误标/重复记录），全部按缺失处理。清洗后数据集中已不存在 `rating = 0 且评论 = 0` 的记录（对应 `verify_clean.py` 的第 ⑥ 项校验）。

## 六、最终数据长什么样

清洗后 **151 个景点**，分布：

|---|---|---|---|
| 西安 | 18 | 4.419 | 179,970 |
| 杭州 | 17 | 4.500 | 13,826 |
| 重庆 | 16 | 4.485 | 37,162 |
| 济南 | 16 | 4.400 | 11,088 |
| 南京 | 16 | 4.581 | 37,162 |
| 上海 | 15 | 4.650 | — |
| 武汉 | 15 | 4.609 | 26,527 |
| 北京 | 14 | 4.644 | — |
| 成都 | 13 | 4.667 | 87,355 |

合计 **608,423** 条评论量，151 个景点里有 **105 个**有评论、46 个评论数为 0。

顺带说清一个容易混淆的地方：这里的 **608,423** 是平台字段 `comment_count` 的求和（"累计有多少条评论"），而我自己抓回来、**实际读过内容的评论文本**是 **1,812 条**（清洗前 499 条时是 **9,058 条**）。两个数字差了三个数量级，因为爬虫只抓了每个景点页面前几页评论。

**这两个口径不能混着用** —— 汇报数据规模用 60.8 万，做文本分析用 1,812。我第一次写简历时把两者和景点数混在一句话里，被自己面试假想追问了一次就露馅了。

## 七、结论本身也不显著，这里一并交代

数据洗干净之后我做了相关性分析，结果是**两个假设都不成立**：

**假设 1：热度高的景点，评价更好？**

```
Pearson  r = 0.1009  (p = 0.2175)   不显著
Spearman ρ = 0.0782  (p = 0.3399)   不显著
高热度组（评论数 Top 20%，n=31）均分 4.671
低热度组（评论数 Bottom 20%，n=46）均分 4.646
Welch t 检验 p = 0.6299             不显著
```

高热度组只比低热度组高 **0.025 分**。这个差距在 151 个样本上完全站不住。

**假设 2：哪些城市口碑更好？**

排名是成都 4.667 最高、济南 4.400 最低，全网均分 4.550，评分 ≥ 4.5 的景点占 **77.5%**。

但看到这个分布我不太敢下"成都口碑最好"的结论——因为每个城市的样本量只有 11~18 个，这个量级的均分标准误太大。**这个排名可以做描述，不能用来支撑"成都景点更好"这种断言。**

## 八、让数字可复现：把结论写进脚本

上面这些数字，我一开始是写在 README 里的。但每次改清洗逻辑，都要手动重算一遍——**这是数字失控的开始**。

所以我把这些全部写进了 `src/stats.py`，里面带 11 项断言：

```python
EXPECT = {
    "n": 151, "comment_total": 608423,
    "pearson_r": 0.101, "spearman_rho": 0.078,
    "n_hi": 31, "n_lo": 46,
    "hi_mean": 4.671, "lo_mean": 4.646,
    "ttest_p": 0.630, "overall_mean": 4.550, "pct_ge_45": 77.5,
}
# ... 计算后逐项比对，任何一项漂移即 sys.exit(1)
```

跑 `python src/stats.py`，输出：

```
【自检】✅ 全部 11 项与 README 基准一致
```

这样做的价值是：**如果哪天清洗逻辑改了、导致 README 里的数字不再是真实的，脚本会直接报错，而不是让一个错数字继续躺在仓库里。**

顺便修掉一个我自己的错误：README 里原来写的是 `r=0.101（p=0.340）`——**r 是 Pearson 算的，p 却是 Spearman 的**。这种"两个统计量张冠李戴"的错误，不写脚本根本发现不了。

## 九、这一版的三条教训

**1. "看起来干净"和"真的干净"是两件事。**
我 v1 的数据通过了去重规则、通过了我自己写的所有校验，但我完全没发现 69.7% 的数据城市归属是错的。**校验规则的天花板 = 你的认知天花板。** 人工逐条看一遍，胜过跑一百条自认为很聪明的规则。

**2. 用假数据做交叉验证，比不做验证更危险。**
我原计划用经纬度校验归属，而经纬度是脚本自己编的。如果那条路"跑通"了，我会得到一个完全错误但看起来很严谨的结论。**做校验之前，先确认被校验的字段本身是真的。**

**3. 主动推翻自己的结论，是这个项目里最有价值的部分。**
上一篇那篇文章我写得挺顺，数据故事完整、结论明确。但它建立在错误的清洗结果上。**如果我不回头看，"污染率 8.8%"这个数字会跟着我进简历、进面试，成为一个随时会塌的雷。**
